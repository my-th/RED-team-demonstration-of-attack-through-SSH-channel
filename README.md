## Project Overview

SSH (Secure Shell) is commonly used to administer Linux systems remotely. A password-guessing attack attempts multiple candidate passwords against an account. Although SSH encrypts the connection, encryption does not prevent an attacker from trying weak or reused passwords.

This project models a small Red Team/Blue Team exercise:

1. The Red Team prepares a Kali Linux workstation and identifies the lab target's SSH service.
2. A controlled authentication test generates login events against a designated test account.
3. A third presenter explains the activity and its potential impact.
4. The Blue Team takes over to inspect telemetry, detect suspicious activity, and apply defensive controls.

**Scope of this README:** Members 1–3 cover the Red Team portion. The Blue Team tools are introduced as the next phase; their installation and configuration should be documented in a separate section or file once implemented.

## Learning Objectives

By completing the lab, participants should be able to:

- Prepare a Kali Linux workstation for a controlled security assessment.
- Confirm connectivity to an explicitly authorized target.
- Identify an exposed SSH service and determine its service version.
- Explain dictionary-based password guessing and how Hydra automates authentication attempts.
- Identify the authentication logs generated by failed and successful login attempts.
- Explain how IDS, centralized log monitoring, rate-limiting, and firewall controls support defense.

## Phase 1 — Member 1: Reconnaissance and Environment Preparation

### Role

Prepare the Kali Linux workstation, verify the required utilities, confirm that the authorized victim is reachable, and identify its SSH service. **Member 1 does not launch the password-guessing test.**

### Step 1: Update Kali Linux

```bash
sudo apt update
sudo apt full-upgrade -y
```

`apt update` refreshes the package index. `apt full-upgrade` updates installed packages and may install or remove packages to resolve dependencies. Review major changes before confirming them on any system you rely on, and take a VM snapshot first if appropriate.

**Presenter notes:**
“Before beginning the assessment, we prepare the workstation and check that the required packages are available. Keeping a lab system maintained reduces avoidable compatibility issues.”

### Step 2: Install the required tools

```bash
sudo apt install -y hydra nmap medusa openssh-client
```

| Tool | Purpose in this lab |
|---|---|
| Hydra | Performs the controlled SSH authentication test in Phase 2. |
| Nmap | Discovers the target's open ports and identifies services. |
| Medusa | Alternative authentication-testing utility; not used in the core demonstration. |
| OpenSSH client | Verifies legitimate SSH connectivity. |

### Step 3: Verify installation

```bash
hydra -h
nmap --version
medusa -h
ssh -V
```

Check that each command displays its help text or version information without an installation error.

### Step 4: Obtain the victim's IP address

On the Ubuntu victim, the Blue Team or lab administrator can run:

```bash
hostname -I
```

Alternatively:

```bash
ip addr
```

Record the correct lab interface address. In the examples below, `192.168.1.20` represents the victim. Replace it with the address confirmed in your environment.

### Step 5: Verify connectivity

From Kali:

```bash
ping <Victim-IP>
```

For example:

```bash
ping 192.168.1.20
```

Stop the continuous ping with **Ctrl+C**. Replies indicate that ICMP connectivity is working; no replies do not necessarily mean the host is down, because ICMP may be filtered.

### Step 6: Discover open ports

Run this only against the authorized lab target:

```bash
nmap <Victim-IP>
```

Example:

```bash
nmap 192.168.1.20
```

Example of a possible result:

```text
PORT STATE SERVICE
22/tcp open ssh
```

This indicates that TCP port 22 is open and Nmap identifies the service as SSH. Actual results depend on the target configuration.

### Step 7: Detect the SSH service version

```bash
nmap -sV <Victim-IP>
```

Example:

```bash
nmap -sV 192.168.1.20
```

Nmap may report a service and version such as `OpenSSH 9.x`. The exact version depends on the target. Version detection is useful for inventory and vulnerability assessment, but a version string alone does not prove that a system is vulnerable.

### Member 1: Findings checklist

- [ ] Kali workstation prepared.
- [ ] Required utilities installed and verified.
- [ ] Victim IP confirmed with the Blue Team.
- [ ] Connectivity checked.
- [ ] SSH service and TCP port identified.
- [ ] Service-version result recorded.
- [ ] Findings handed over to Member 2.

**Handover script**

> “We have completed reconnaissance and confirmed that the authorized lab target exposes an SSH service. The attacker workstation is prepared, and the target details have been recorded. I will now hand over to Member 2, who will conduct the controlled authentication test.”

## Phase 2 —: Controlled SSH Authentication Test

### Role

Verify that the SSH service supports legitimate access, prepare a small password dictionary for the lab, and initiate the authorized authentication test. This phase must remain within the isolated environment and use only the designated test account.

### Step 1: Verify legitimate SSH access

```bash
ssh demo@<Victim-IP>
```

Example:

```bash
ssh demo@192.168.1.20
```

Use the password configured for the lab's `demo` account. On first connection, SSH may ask you to verify the server's host key. Confirm the fingerprint through a trusted lab method before accepting it.

After login, the prompt may resemble:

```text
demo@victim:~$
```

Exit the session:

```bash
exit
```

**Presenter notes:**
“Before testing authentication defenses, we verify that normal SSH access works. This gives us a baseline and helps distinguish a service configuration problem from behavior caused by the test.”

### Step 2: Create a small lab-only password dictionary

Create a file in the working directory:

```bash
nano passwords.txt
```

For a disposable lab account only, enter a few test values, for example:

```text
123456
password
admin
qwerty
letmein
<LAB_TEST_PASSWORD>
```

Replace `<LAB_TEST_PASSWORD>` with the password deliberately configured for the disposable `demo` account in your lab. Do not use a real person's password or credentials from a production system.

Save in Nano with **Ctrl+O**, press **Enter**, then exit with **Ctrl+X**.

### Step 3: Verify the dictionary

```bash
cat passwords.txt
```

Check that the file contains only the intended test values. Avoid placing real credentials in the repository or committing `passwords.txt` if it contains a usable lab password.

### Step 4: Explain Hydra

Hydra is a network login-testing utility that automates authentication attempts against supported services, including SSH. It does **not** break SSH encryption. It submits candidate credentials to the SSH service and receives authentication results.

For a safe demonstration, use a deliberately small dictionary, a disposable test account, a private lab network, and a bounded test window. Stop the test once the expected telemetry has been collected or a defensive control triggers.

### Step 5: Run the controlled test

**Authorized isolated lab only.** Confirm that the target is your own disposable VM and that the Blue Team is ready to monitor before starting.

```bash
hydra -l demo -P passwords.txt ssh://<Victim-IP>
```

Example target syntax:

```bash
hydra -l demo -P passwords.txt ssh://192.168.1.20
```

Command breakdown:

- `hydra` starts the tool.
- `-l demo` selects the lab test username.
- `-P passwords.txt` supplies the lab dictionary.
- `ssh://<Victim-IP>` specifies the SSH service and target.

The output and behavior vary by Hydra version, SSH configuration, network conditions, and defensive controls. Do not assume that a particular line or timing will appear exactly as shown in a presentation.



### Important interpretation

A dictionary-based test tries candidate passwords from a list. “Brute force” is often used broadly in conversation, but a dictionary attack is specifically list-based; exhaustive brute force systematically explores a defined password space. Neither technique bypasses SSH encryption simply by making repeated login attempts.

**Handover script**

> “The controlled authentication test has been initiated and is generating events for the Blue Team to inspect. I will hand over to Member 3 to explain the activity, its potential impact, and the evidence defenders should look for.”

## Phase 3 —: Attack Observation and Threat Analysis

### Role

Member 3 does not install tools or start a second test. Observe the test already initiated by Member 2, explain the workflow, discuss the risk, and prepare the transition to the Blue Team.

### Step 1: Observe the test output

The terminal may show progress, authentication outcomes, or connection errors. The exact output depends on the tool version and target configuration. Avoid presenting illustrative output as a guaranteed transcript.

Hydra is attempting candidate credentials from the configured list. The SSH server evaluates the requests and returns authentication results.

### Step 2: Explain how SSH handles the activity

Hydra does not decrypt the SSH session. It repeatedly submits authentication attempts over the SSH connection. The server accepts or rejects each attempt according to its account, password, and security configuration.

The process ends when the candidate list is exhausted, the test is stopped, a valid credential is found, or connectivity/security controls prevent further attempts.

### Step 3: Explain the workflow

```text
Small lab password list
|
v
Hydra
|
v
SSH service (TCP 22)
|
v
Authentication outcome
/ \
v v
Failed Successful
| |
v v
Next test Lab account access
|
v
SSH authentication logs
|
v


Each attempt can create an authentication event. Failed-login records and surrounding telemetry can help defenders identify a pattern rather than treating each event in isolation.

### Step 4: Explain the potential impact

If an attacker guesses a valid password on a real system, the resulting access may enable them to:

- Read or alter data available to the compromised account.
- Access confidential files.
- Run unauthorized commands or deploy malware within the account's permissions.
- Attempt privilege escalation if other weaknesses exist.
- Use the compromised host as a foothold for further movement, depending on network access and controls.

These outcomes are risks, not automatic consequences. The actual impact depends on account privileges, system hardening, segmentation, and monitoring.

### Step 5: Explain authentication logs

On many Ubuntu systems, SSH authentication events can be found in `/var/log/auth.log`. On systems using systemd journal logging, the following may also be useful:

```bash
sudo journalctl -u ssh
```

A failed authentication record may resemble:

```text
Failed password for demo from 192.168.1.10 port 53642 ssh2
```

This is an illustrative example, not a guaranteed exact log line. Depending on configuration, logs can help identify:

- The account name involved.
- The source IP address.
- The event time.
- Whether authentication succeeded or failed.
- Related connection details.

Avoid sharing logs publicly if they contain real usernames, public IP addresses, hostnames, or other sensitive information.


### Step 6: Explaination why detection matters

Strong passwords are important, but they are only one layer of defense. Organizations should also use SSH keys where appropriate, disable password authentication when feasible, limit access to trusted networks, monitor authentication events, apply rate limits, and keep systems updated.

**Presenter notes:**
“The important lesson is that authentication attempts leave evidence. Defenders combine host logs and network telemetry to identify suspicious patterns, alert administrators, and apply proportionate response measures.”

## Security Notes and Cleanup

- Keep the lab isolated from production systems and public targets.
- Use disposable VMs and a dedicated, low-privilege test account.
- Use only a small, controlled test dictionary.
- Stop the test after the required evidence is collected.
- Remove the lab test account and test password file when the exercise is complete.
- Revert VMs to clean snapshots if appropriate.
- Do not commit credentials or sensitive logs to GitHub.
- Treat scan and authentication results as evidence from this specific lab, not proof that a system is generally secure or vulnerable.

## Troubleshooting

| Symptom | Checks |
|---|---|
| `ping` receives no replies | Confirm the IP address and network mode; ICMP may be filtered, so use authorized service checks as well. |
| Nmap does not show port 22 open | Verify that the SSH server is installed, running, listening on the expected interface, and allowed by the lab firewall. |
| SSH connection is refused | Check the SSH service status on Ubuntu and confirm the target IP and port. |
| SSH times out | Check VM network connectivity, routing, and firewall rules. |
| Hydra reports connection errors | Stop the test and verify that SSH is reachable, the lab target is correct, and no control has blocked the connection. Do not increase attack volume to work around a defense. |
| No monitoring alert appears | Verify log collection, rule configuration, sensor placement, and timestamps. Tool installation alone does not guarantee an alert. |



Keep only sanitized, intentional evidence in the repository. If you add screenshots, label them clearly and redact sensitive information.

## Conclusion

This project demonstrates the relationship between offensive testing and defensive monitoring. Reconnaissance identifies exposed services; a controlled authentication test produces observable events; and the Blue Team uses logs, network alerts, and response controls to investigate and reduce risk.

The goal is not simply to run an attack tool. It is to understand what the activity looks like, what evidence it leaves behind, and how layered security controls can help prevent unauthorized access.
